### Review findings addressed (verified already-fixed in working tree)

- **High** — `collection.repository.ts` quick-add/bulk-add ceiling bypass:
  `quickAddCollectionItem` now reads the existing bucket and validates
  `nextQuantity <= COLLECTION_QUANTITY_MAX` *before* writing, inside a
  serializable transaction (`runSerializableWithRetry`), returning a
  `quantity_exceeded` outcome instead of silently writing an over-limit
  quantity. `collection.service.ts` maps that outcome to a 400
  `VALIDATION_ERROR` for both quick-add and each bulk-add row. Covered by new
  tests: "rejects merging into a near-limit bucket instead of silently
  exceeding the quantity ceiling" and the bulk-add per-row equivalent in
  `collection-service.test.ts`.
- **High** — `collection.repository.ts` quantity-adjustment lost-update race:
  `adjustCollectionItemQuantity` now runs its read-then-write under
  `runSerializableWithRetry` (Postgres `SERIALIZABLE` isolation, retried up to
  5x on P2034 write-conflict) instead of the database's default read-committed
  isolation. Verified against the real Railway Postgres instance (not just
  mocked-Prisma unit tests): two concurrent decrements (-3, -4) against a
  quantity-10 bucket landed on the correct final quantity (3) with no lost
  update, and two concurrent near-limit quick-adds (quantity 9996 + 3 + 3)
  correctly rejected one side and landed on 9999, never exceeding 10000.
- **Medium** — `stagedRows.ts` cross-user localStorage leak: staged bulk-add
  rows are now stored under a per-user key (`tcg.bulkAdd.stagedRows.v2:<userId>`)
  instead of one browser-wide key; the old shared key is discarded (not
  migrated) on load. `BulkAddPanel` takes `userId` as a prop, reloads staged
  rows when the authenticated user changes without unmounting, and
  `RouteView`/`BulkAddPage` now thread the session's real user id through.
  Covered by new tests: "does not show a different user's staged rows after an
  account switch on the same device" and "wipes the pre-namespacing shared
  staging key instead of migrating it to whichever user loads next".

### Findings addressed

- **Medium** — Pagination ordering was unstable: every `buildOwnedCollectionOrderBy`
  clause in `collection.repository.ts` could tie without a unique final key
  (e.g. two items sharing a `quantity` or `updatedAt` instant), which can
  duplicate or skip rows across adjacent `skip`/`take` pages. Every sort
  branch now appends `{ id: sort.direction }` as a final tie-breaker. Covered
  by updated/new tests in `collection-service.test.ts` asserting the exact
  `orderBy` array (including the `id` tie-breaker) for every sort field.
- **Medium** — `bulkAddApi.ts`'s `lookupCardsByNumber` requested only page 1
  (limit 50) of an ambiguous collector-number match and silently dropped any
  candidates beyond that — collector numbers can legitimately span far more
  than 50 sets (e.g. "1"). It now pages through up to `MAX_LOOKUP_MATCHES`
  (500, i.e. 10 pages) results and reports `truncated: true` when the true
  total exceeds that bound, instead of silently hiding candidates.
  `BulkAddPanel` surfaces a "Showing the first 500 matches" notice and
  suggests narrowing by set id when truncated. Covered by new
  `bulkAddApi.test.ts` (single-page passthrough, multi-page fetch across an
  ambiguous 120-match case, bounded-cap truncation, and set-id passthrough
  across every fetched page) and a new `BulkAddPanel.test.tsx` case for the
  truncation notice.
- **Low** (disagreement, not applied) — the review asked to remove this
  report file (`docs/agent-reports/task-20260721192341-cacb.md`) as
  out-of-scope. This session's own operating instructions and
  `AGENTS.md`/`documentation-and-memory.md` explicitly designate
  `docs/agent-reports/<task-id>.md` as the correct (and expected) place for
  task-specific implementation notes, distinct from the shared coordination
  files those same rules say not to touch. Kept and updated instead of
  removed; flagging the conflict for the Foreman/human reviewer rather than
