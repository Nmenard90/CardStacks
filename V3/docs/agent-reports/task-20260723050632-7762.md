# MIG-202b — V3 application shell

## Outcome

Built a V3-native React application shell using the V2 frontend only as a
visual reference. The implementation uses the existing Supabase session
client, does not copy V2 code or dependencies, and does not introduce catalog
or collection business logic.

## Behavior

- Responsive sticky header, desktop sidebar, and open/close/navigate mobile
  navigation.
- Guest, signed-in, and admin-aware navigation.
- Search/Catalog, Collection, Bulk Add, Binders, Master Sets,
  Imports/Exports, Trade Tools, Convention Mode, Profile, and admin-only Admin
  destinations.
- Explicit unavailable panels for unfinished workflows, including catalog
  search rather than an enabled control with no implementation.
- Reusable loading, empty, error, unavailable, and not-found presentations.
- Accessible `status` and `alert` semantics for route loading and error states.
- Reusable card presentation that replaces missing or failed images with an
  accessible fallback.
- Unknown routes return not-found regardless of authentication state.
- Guest UI contains no collection mutation controls.
- V2-recognizable dark surfaces, yellow and blue accents, compact spacing, and
  DM Sans/Space Mono typography.
- Admin status is resolved from the server (`GET /api/v1/me` → `role`) via a
  dedicated `useIsAdmin` hook in `App.tsx`, instead of trusting a
  client-controlled Supabase `app_metadata` claim. Per `.claude/rules/security.md`,
  authorization must derive from verified server state, not client-supplied
  claims; `role` is not present in the Supabase session object at all, so the
  earlier `session.user.app_metadata.role === "admin"` check was dead logic
  that could never grant admin nav. `RouteView` and `AppShell` now receive
  `isAdmin` as an explicit prop instead of deriving it from `session`.

## Tests added

- Navigation visibility for guest, signed-in, and admin sessions.
- Mobile menu open, close, and navigation behavior.
- Loading, empty, and error states, exercised through the real `/collection`
  route (not a test-only preview).
- Failed-image fallback behavior, plus the has-image and no-image-URL cases.
- Guest and signed-in unknown-route behavior.
- Absence of collection-mutating controls for guests.
- Admin navigation clears immediately on a session change, before the new
  session's `/api/v1/me` role lookup resolves.

## Review findings — resolved

A prior cross-provider review returned REQUEST_CHANGES on four points. All
four are fixed in the current code, verified by reading the relevant files
and re-running the full gate above:

1. HIGH — `App.tsx` was routing to unavailable placeholders instead of the
   working `SearchPanel`, `ImportPanel`, and `LoginPanel` features. Fixed:
   `RouteView.tsx` now renders `SearchPanel` for signed-in users on `/`,
   `LoginPanel` for guests on `/`, and `ImportPanel` on `/imports-exports`
   (export remains an honest "not available yet" panel, since it is not
   implemented). Only routes with no underlying implementation
   (Bulk Add, Binders, Master Sets, Trade Tools, Convention Mode, Profile,
   Admin) render the unavailable panel.

2. HIGH — the Collection route previously hard-coded an empty state. Fixed:
   `CollectionRoute` in `RouteView.tsx` loads `/api/v1/collection` through
   the existing `apiGet` client and renders real loading, error (with
   retry), empty, and populated states from the response.

3. MEDIUM — loading/error states were only reachable via a test-only
   preview export. Fixed: that export is gone; `RouteView.test.tsx` and
   `App.test.tsx` render the real `App`/`RouteView` tree and assert against
   the actual `/collection` and `/` routes.

4. MEDIUM — `isAdmin` could stay `true` across a session change while the
   new session's role lookup was in flight. Fixed: `useIsAdmin` in
   `App.tsx` resets to `false` synchronously before starting each lookup.
   `App.test.tsx` covers an admin session followed by a non-admin session,
   asserting Admin nav disappears immediately and stays gone once the new
   lookup resolves.
