# MIG-201-REVIEW — migration audit verification

## Scope and acceptance criteria

Independently compare `docs/MIGRATION_AUDIT.md` with the legacy React/Scala implementation and the active V3 source. Verify route and feature coverage, missing behavior, security/data-integrity concerns, and whether MIG-202 can deliver its stated authenticated collection-tracker slice. This review changes documentation only.

## Review result

The audit's broad inventory is reliable:

- The seven legacy browser routes declared by `../web/src/App.tsx` are all represented.
- The 23 legacy HTTP routes are all represented: seven card/catalog/admin routes, five collection routes, six binder routes, four user routes, and `/health`.
- The source supports the important distinctions that marketplace behavior is repository/model-only, convention reports are local-only, the legacy user-id-in-path authorization model is unsafe, V3 uses authenticated ownership, and read-triggered legacy catalog/price mutation should not be restored.
- The V3 gaps around binder update/delete/bounds, public binder DTO allowlisting, CSV formula protection, XLSX placeholder behavior, import/export UX, background-job operational guarantees, and the minimal non-routed V3 web shell are accurately identified.
- No schema migration is needed for a basic MIG-202 collection tracker.

## Required corrections and omissions

1. **Correct the V3 quantity limit.** The audit twice describes V3 collection quantity as `1..999` (the single-write mapping and collection integrity ledger). `apps/api/src/modules/collection/collection.schemas.ts` actually accepts quick-add quantities `1..10000`, update quantities `0..10000`, and treats update quantity zero as deletion. MIG-202 must use the implemented bound unless a separately tested contract change is approved.

2. **MIG-202 cannot directly edit condition or variant through the existing update contract.** `PATCH /api/v1/collection/items/:itemId` accepts only `quantity`, `storageLocation`, and `notes`. Condition and variant are part of the collection bucket identity and are accepted only by quick-add. MIG-202 must explicitly choose and test either an owner-scoped API operation that moves/replaces a bucket without loss or a compensating add-then-delete client workflow with conflict, rollback, and partial-failure handling. It must not present condition/variant editing as already supported by the existing PATCH route.

3. **Define what MIG-202 “stats” means.** `GET /api/v1/collection/summary` currently returns only total quantity, bucket count, and grouping by condition. It does not return legacy unique-card count, owned-set count, or collection value, and collection list rows do not include prices. MIG-202 must either limit acceptance to the existing count summary and visibly defer valuation/set statistics, or add a bounded server-side summary contract for the required statistics. Fetching prices once per card in the browser is not an acceptable large-collection implementation.

These are required MIG-202 scope corrections; the remaining audit classifications and restoration order are sufficiently accurate to proceed once they are carried into MIG-202 acceptance criteria.
