# Task task-20260721192341-a777 — MIG-203 review follow-up

## Scope

Resolve the actionable findings from the independent review of MIG-203
(catalog, set browsing, search, card detail, and card images). This session
only addressed the review findings below; it did not re-implement or expand
MIG-203 itself.

## Findings addressed

1. **High — `CatalogSearch.tsx` ambiguous results had no pagination.**
   Matches beyond the first 25 candidates for an ambiguous collector number
   were unreachable. Added the shared `PageControls` (from
   `features/catalog/SetBrowser.tsx`) to the ambiguous-results branch, and
   refactored the non-ambiguous branch to use the same component instead of
   duplicating the prev/next markup. Added a test
   (`CatalogSearch.test.tsx`) that renders an ambiguous, multi-page result
   and asserts the "Next" control requests page 2 with the same filters.

2. **High — `SearchPanel.tsx` (signed-in landing page) always sent the
   query as `q`.** Set ids, set names, and collector numbers typed into the
   placeholder-advertised search box were being searched as card-name
   prefixes, silently returning nothing. Rewrote `SearchPanel` to use the
   same four-field contract as `CatalogSearch`/`searchApi.searchCards`
   (`q`, `setId`, `setName`, `number`), `hasMeaningfulSearchFilter` for
   inline validation, and `PageControls`/`groupCandidatesBySet` for
   pagination and ambiguity, while preserving the existing quick-add flow
   (fetch card detail, add first variant near-mint). Added
   `SearchPanel.test.tsx` covering: set-id-only search sent as `setId`,
   number-only search sent as `number`, empty-submission rejection, and the
   quick-add round trip.

3. **Medium — `RouteView.tsx` uncaught exception on malformed URL
   escapes.** `decodeURIComponent` was called directly on the `/catalog/:id`
   and `/cards/:id` path segments during render; a path like `/cards/%`
   throws `URIError` and would crash the app. Added `safeDecodeSegment`,
   which catches the decode failure and returns `null`, and an
   `InvalidPathPanel` not-found state rendered in that case (no API call is
   made). Added parametrized tests in `RouteView.test.tsx` for
   `/cards/%` and `/catalog/%` confirming a not-found panel renders and
   `apiGet` is never called.

4. **Medium — verification evidence gap.** The prior report did not record
   full `pnpm lint` / `pnpm build`, so this session re-ran the complete
   required command set after the fixes above (see Verification). Browser,
   Railway production acceptance, and manual keyboard/mobile/broken-image
   scenarios still require an environment with a running dev server and
   browser; they were not exercised in this shell-only session — see
   Known limitations.

## Known limitations

- The browser/production-acceptance checks required by the MIG-203 task
  description were not exercised here; this was a targeted fix for the
  independent review's automated-scope findings. A session with a running
  dev server and browser should still complete the manual pass before
  merge.
- `SearchPanel` and `CatalogSearch` now both implement the four-field
  search form and pagination/ambiguity rendering. They are not merged into
  one shared component because `SearchPanel` also owns the quick-add
  action, which `CatalogSearch` intentionally does not have (it navigates
  to the card detail page instead). This is a deliberate, minimal-diff
  choice, not an oversight — a future consolidation could extract a shared
  results-list component if the duplication becomes a maintenance problem.
