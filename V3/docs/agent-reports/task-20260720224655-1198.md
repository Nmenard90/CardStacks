## Implementation summary (as inherited and verified)

1. **`apps/worker/src/commands.ts`** (new) — `WORKER_COMMANDS` maps the explicit CLI strings `sync-catalog` / `sync-prices` to `syncCatalog` / `syncPrices`. `resolveWorkerCommand()` throws `Unknown worker command: <name|missing>` for anything else, so an invalid invocation fails immediately instead of silently no-op'ing. Split out of `index.ts` so it is importable in tests without triggering the process entry point's side effects.
2. **`apps/worker/src/index.ts`** (modified) — `main()` now calls `resolveWorkerCommand(command)` and awaits the resolved job; the `if/else` dispatch chain that duplicated `commands.ts` was removed. The top-level `main().catch(...)` still sets `process.exitCode = 1` on any rejection (env validation failure, unknown command, or job failure), so the process exits nonzero without swallowing the error.
3. **`apps/worker/package.json`** (modified) — added `start:sync-catalog` (`node dist/index.js sync-catalog`) and `start:sync-prices` (`node dist/index.js sync-prices`) production start commands alongside the existing generic `build` (`pnpm --filter @tcg/shared build && tsc -p tsconfig.json`) and `start` scripts. The Railway `startCommand` in each `railway.*.toml` invokes these exact script names, keeping the mapping in one place.
4. **`apps/worker/Dockerfile`** (new) — multi-stage build:
   - `deps` stage copies `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `turbo.json`, and the three relevant workspace `package.json` files, then runs `pnpm install --frozen-lockfile` (satisfies "uses the lockfile").
   - `build` stage runs `pnpm --filter @tcg/db db:generate` (generates the Prisma client before compilation), then builds `@tcg/shared` and `@tcg/worker`.
   - `runner` stage sets `NODE_ENV=production` and defaults `CMD` to `pnpm --filter @tcg/worker start`, which has no argv command and therefore throws `Unknown worker command: missing` and exits nonzero if the image is run without a Railway-supplied `startCommand` override — deliberately fails fast rather than doing nothing.
5. **`apps/worker/Dockerfile.dockerignore`** (new) — scoped ignore file (Docker resolves `<Dockerfile-path>.dockerignore` relative to build context) excluding `node_modules`, `dist`, `.turbo`, `coverage`, `.git`, and `.env*` (with `.env.example` allowed) from the build context.
6. **`apps/worker/railway.catalog-sync.toml`** / **`apps/worker/railway.price-sync.toml`** (new) — Railway config-as-code per service: `dockerfilePath`, explicit `startCommand` (`start:sync-catalog` / `start:sync-prices`), `cronSchedule` (marked `TBD` placeholders pending a real product cadence decision — 12h catalog / 6h price — with rationale comments), `restartPolicyType = "NEVER"` (the container runs one job to completion and exits; it is not a long-lived service), and a documented list of required environment variables (names only, no values, per the security rules).
7. **`apps/worker/src/tests/command-dispatch.test.ts`** (new) — 5 unit tests: `sync-catalog` and `sync-prices` resolve to the correct job functions, a missing command throws (matches `/missing/`), an unrecognized command throws with its own name in the message, and `WORKER_COMMANDS` exposes exactly the two expected keys.

`apps/worker/src/jobs/sync-catalog.ts` and `apps/worker/src/jobs/sync-prices.ts` were pre-existing (not part of this task's diff) and already satisfy "exits nonzero on failed jobs and records failure state": both create a `SyncRun` row (`status: "RUNNING"`), and on any thrown error write a `SyncError` row and update the `SyncRun` to `status: "FAILED"` with an `errorSummary` before re-throwing, which propagates to `main()`'s `.catch()` and sets `process.exitCode = 1`.

## Review round 2 — reviewer findings and fixes

A cross-provider review of the committed changes returned three findings, all resolved in this session:

1. **P1 — `sync-prices` recorded `PARTIAL_FAILURE` but resolved successfully, so the process exited 0 despite a failed job.** Fixed in `apps/worker/src/jobs/sync-prices.ts`: after recording the `SyncRun` as `PARTIAL_FAILURE`, the function now unconditionally throws (outside the existing try/catch, so the throw doesn't get relabeled `FAILED`). This propagates through `main()`/`runWorker()` and sets `process.exitCode = 1`, matching the "exits nonzero on failed jobs" acceptance criterion for every current invocation of this scaffold job.
2. **P1 — `railway.price-sync.toml` actively scheduled the unfinished scaffold every six hours.** Fixed: `cronSchedule` is now commented out with an explanation (job is a scaffold, PRICE-703 not implemented, SPEC.md §10 requires provider mappings/overlap protection to be tested before a worker schedule is deployed). The service definition (`startCommand`, `restartPolicyType`, required env vars) remains so it is ready to enable once PRICE-703 ships.
3. **P2 — no test proved a rejected/failed job produces a nonzero process exit; existing tests covered only command lookup.** Fixed: `apps/worker/src/index.ts` now exports `main` and `runWorker` (the `main().catch(...)` wiring that sets `process.exitCode`), guarded by a direct-execution check (`import.meta.url` vs. `pathToFileURL(process.argv[1])`) so importing the module in tests stays side-effect-free. New `apps/worker/src/tests/entry-point.test.ts` mocks `resolveWorkerCommand`/`loadWorkerEnv`/`PrismaClient` and asserts `runWorker()` sets `process.exitCode = 1` when the resolved job rejects and when env validation throws, and leaves it untouched on success.

## Review round 3 — reviewer finding and fix

A further cross-provider review of the round-2 commit returned one finding, resolved in this session:

1. **P1 — `railway.catalog-sync.toml` actively scheduled catalog sync every 12 hours despite `docs/SPEC.md` §10 prohibiting a worker schedule until overlap protection is tested, and `syncCatalog` (`apps/worker/src/jobs/sync-catalog.ts`) has no concurrency guard.** Two overlapping triggers (e.g., a slow run plus a new scheduled trigger) could race on the same `Set`/`Card`/`CardVariant` upserts. Fixed: `cronSchedule` in `apps/worker/railway.catalog-sync.toml` is now commented out, mirroring the existing `railway.price-sync.toml` pattern, with a comment explaining the missing concurrency guard and pointing at `CAT-302` ("Optimize catalog synchronization" — acceptance criterion "Concurrent catalog runs are prevented") as the tracked follow-up that must land before a schedule is enabled. `startCommand`, `restartPolicyType`, and the required-environment-variable list are unchanged so the service definition is ready to enable once `CAT-302` ships.

Implementing real overlap protection for `syncCatalog` itself is out of this task's scope (`CAT-302` is a separate, dependent backlog item); this fix only removes the premature schedule per `docs/SPEC.md` §10.
